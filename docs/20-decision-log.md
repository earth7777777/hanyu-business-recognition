# 决策记录

> 这是项目内容文件，不是规则文件。这里只记已经确认并仍然生效的关键决定；如果后续决定改变了现行规则，还要同步回写 `00-project-brief` 和 `10-scope-and-rules`。

## 当前仍生效的关键决定

| 日期 | 决定 | 替换了什么旧口径 | 原因 |
| --- | --- | --- | --- |
| 2026-03-19 | 当前上线主线明确为 **金蝶手动导出 Excel -> 系统导入 -> 识别归一化 -> 审计核对 -> 提醒判断**。 | 不再把 PDF / 图片 / OCR 当作当前上线主线。 | 先走最短可落地路径，尽快满足姚建锋当前业务需求。 |
| 2026-03-19 | 当前主输入源正式定为 **Excel**。图片、PDF、OCR 作为后续补强能力，暂不掺进当前主线。 | 从“多输入源一起推进”改为“先稳 Excel 主链”。 | Excel 最容易稳定导入、最快上线、最利于验证字段与规则。 |
| 2026-03-19 | 当前业务主目标只围绕两条提醒：**临近交期未发货**、**发货后两个月未开票**。 | 不再把其它延伸能力提前并入当前主目标。 | 先聚焦姚建锋最急的两条提醒，避免范围失控。 |
| 2026-03-19 | 上传入口必须 **人工手选单据类型**，固定 4 类：合同订单=`order`、发货单=`shipment`、付款通知单=`payment_notice`、发票=`invoice`。 | 替换掉“默认第一项就是 order 的静默上传”。 | 自动猜类型容易误判，先让人明确指定，降低发票误识别成订单的风险。 |
| 2026-03-19 | 当前上传入口选择的是 **单据类型**，不是文件格式。 | 不再把“Excel/PDF/图片”直接混成上传入口类型。 | 文件格式和业务单据类型是两件事，混在一起会把前后端逻辑搞乱。 |
| 2026-03-19 | 多文件上传采用 **前端多选 + 前端逐个调用现有单文件接口** 的最小方案。 | 不重写后端多文件接口，不重构上传链。 | 保住现有 job / 审计 / 去重 / 软删除链路，风险最小。 |
| 2026-03-19 | 当前页面定位为 **验收/操作后台**，不是最终员工正式工作台。 | 不把当前测试页直接当成最终角色化员工页面。 | 先把后端能力和验收链跑稳，再做正式前端页面与角色入口。 |
| 2026-03-19 | 当前重复处理主线定为：**严格重复由系统自动删并保留最小留痕；前台不再保留“查看重复来源”作为主操作入口**。 | 不再沿用“发现重复 -> 查看重复来源 -> 人工决定是否软删除”的旧前台主路径。 | 月总已确认：现在最重要的是让系统自动判重、自动清理、留下数字，而不是让人长期在前台追着看重复来源。 |
| 2026-03-19 | 删除策略采用 **文件级软删除**，不做物理硬删，不做 Job 级删除。 | 不允许直接“删数据库”或直接硬删文件记录。 | 先保住可回退能力，避免误删后无法核对。 |
| 2026-03-19 | “显示已删除文件”只控制 **展示口径**，不触发 Normalize / Match / Alert 重算。 | 不把软删除展示切换误做成业务重算入口。 | 先保证审计与回收站逻辑清楚，避免展示动作污染业务结果。 |
| 2026-03-20 | 审计后台口径定为：文件列表与关联摘要都必须跟随 `include_deleted` 同步切换。 | 不再允许“文件表按未删除口径、摘要表按全量历史口径”这种打架状态。 | 同一页面口径不一致会直接误导人工判断。 |
| 2026-03-20 | 右侧详情与审计信息面板必须始终跟随当前选中的 `file_id` 刷新。 | 不再接受“左边是当前文件、右边挂旧文件信息”的串线状态。 | 审计后台的核心就是点谁看谁，不能靠刷新碰运气。 |
| 2026-03-20 | Job 列表“任务状态”改为按 **文件状态汇总显示**。 | 不再依赖 `latest_task_status` 硬撑，也不允许多文件 job 出现空白。 | 多文件批次需要看到整体状态，不能靠点进去逐条猜。 |
| 2026-03-20 | Job 列表“任务状态”中文化，但只改这一列，不顺手扩大整页。 | 不再长期保留英文状态词作为验收主视图。 | 方便当前高频测试和快速判断。 |
| 2026-03-20 | 当前前端时间显示统一按 **北京时间（Asia/Shanghai）** 格式化。 | 不再在页面直接裸露带 `T` 的原始时间字符串。 | 先统一显示口径，让人能直接看懂时间。 |
| 2026-03-20 | 当前用户可见英文采取 **前端显示层中文化** 的方式处理；`job_id / file_id / task_id` 等编号值本体保留。 | 不再让筛选项、状态词、摘要区、重复来源等主要可见区域长期裸露英文。 | 先提升可读性，同时保留排查所需编号。 |
| 2026-03-20 | 当前系统允许 Excel 存在垃圾列、杂项列、无关列，导入时应 **抓关键列、忽略无关列**。 | 不要求员工先把 Excel 手工清洗到极致才允许导入。 | 实际业务里很难拿到完美纯净表，系统必须自己做过滤。 |
| 2026-03-21 | `document_type=order` 必须启用 **有效订单行门禁**：至少满足一类身份锚点且至少满足一类业务信号，才算有效行。 | 替换掉“任意一个映射字段不空就入库”的宽松规则。 | 堵住半空行、垃圾行进入数据库和污染提醒链。 |
| 2026-03-21 | `parsed_count` 和 `/records` 返回值应反映 **过滤后的真实有效行数**。 | 不再把原始 Excel 粗暴吃成记录数。 | 让页面、接口和数据库对有效行口径保持一致。 |
| 2026-03-21 | 订单关键字段正式纳入第一步补强范围：整单关闭、行关闭、最近出库日期、行已执行已出库数量、行已开票数量、行未开票数量、行开票状态、预计交货日期、单据编号/客户订单号等。 | 不再把这些字段当“以后观察一下”的候选项。 | 这些字段在金蝶导出的 Excel 中基本会有，已足够作为当前正式字段接入。 |
| 2026-03-21 | 第一阶段字段补强策略定为：**先不大拆数据库**，优先把新字段落入 `normalized_records.payload_json`。 | 不先重构成全新订单主表/明细表体系。 | 先吃进去、存住、能查，再决定后续是否需要更重结构。 |
| 2026-03-21 | 字段落库采用两层：`payload.core.*` 保存规范值，`payload.ext.*_raw` 保存原始文本。 | 不再只留原始文本，也不只留规范值。 | 既方便后续规则判断，也方便审计时核对“原表写了什么、系统理解成了什么”。 |
| 2026-03-21 | 关闭状态规则定为：**有列就按值用，缺关闭列才记 `null/未知`，不准硬猜未关闭**。 | 不再允许因为缺列就默认“未关闭”。 | 防误报是当前第一优先。 |
| 2026-03-21 | 业务上“关闭状态 / 行关闭状态”属于 **必填信息**；当前要兼容的异常是 **整列没导出来**，不是“列在但单元格空着”。 | 不再把“值为空”当成常态主流程。 | 和真实业务情况保持一致，避免设计错场景。 |
| 2026-03-21 | 行开票状态必须同时保留原始值和规范值；至少覆盖 **全部开票 / 部分开票 / 未开票** 的规范化映射。 | 不再接受 `line_invoice_status_raw` 已有值但 `core.line_invoice_status` 仍为 `null` 的半收口状态。 | 开票判断后续要接提醒，不能只存原文不做归一化。 |
| 2026-03-21 | 当前实施顺序正式拆成两步：**第一步先做字段导入映射与归一化补强；第二步再把这些字段正式接进提醒过滤逻辑。** | 不允许字段刚入库就立刻和提醒逻辑一起大改。 | 先把数据链跑稳，再改业务判断，能大幅降低炸链风险。 |
| 2026-03-21 | 第二步提醒逻辑尚未开工前，未知状态不进入正式提醒；后续如有需要，再单独设计“待核对/可疑池”。 | 不把“未知”直接混进正式提醒，也不拿预计交货日期直接替代关闭状态。 | 先保守防误报，后续再平衡漏报问题。 |
| 2026-03-21 | 当前第一步已以真实 Excel 样本通过验收：关键字段已成功入库，半空垃圾行被挡掉，`line_invoice_status` 也已完成规范化。 | 不再把第一步视为“还没收口”。 | 现在可以把后续重心转到第二步提醒过滤接入。 |
| 2026-03-23 | 在第二步提醒过滤正式接入前，先把“发货后未开票”这条提醒的默认业务阈值锁定为 **60 天**。 | 不再沿用旧默认值 `7` 天。 | 先把最小且已确认的业务阈值改准，避免旧默认值继续误报。 |
| 2026-03-23 | 第二步提醒过滤改按 **order 行硬数字** 落地：`shipment / payment_notice / invoice` 当前不是提醒结果的硬判断依据。 | 替换掉“第二条提醒主要看付款通知单 / 正式发票信号”的旧口径。 | 当前真实业务更稳的事实源在订单 Excel 行级数字，先按硬数字把提醒跑准。 |
| 2026-03-23 | **临近交期未发货** 正式口径定为：`quantity != executed_shipped_qty` 且进入 `due_before_ship_days` 提醒窗口时触发。 | 不再以 shipment 累加结果作为这条提醒的主判断依据。 | 这轮提醒主线已切到订单行硬数字，减少跨单据拼接带来的漂移。 |
| 2026-03-23 | **出库后 60 天未开票** 正式口径定为：`executed_shipped_qty > 0`、`latest_outbound_date >= 60 天`、且 `uninvoiced_qty > 0` 时触发。 | 替换掉“付款通知单缺失 / 正式发票缺失就报警”的旧口径。 | 当前真实业务里“未开票数量”比票据到没到更能直接表达风险。 |
| 2026-03-23 | `order_closed / line_closed` 本轮只作展示参考，不参与两条提醒的硬过滤。 | 替换掉“已关闭就直接排除”的旧方向。 | 真实金蝶数据已出现“行未开票数量 > 0，但行关闭状态 = 已关闭”，若直接拦截会漏报。 |
| 2026-03-23 | 同一订单 / 同一行多次上传时，按 `line_key` 做最新覆盖；优先级为 `biz_date` > `created_at` > `source_row`，旧记录保留审计不删除。 | 不再继续沿用“每条 order 记录各算各的”旧机制。 | 让后补的新 Excel 能覆盖旧提醒，避免旧状态一直挂着。 |
| 2026-03-23 | 本轮确保 **order 上传可自动触发重算**；是否让其它单据在后续参与更多重算触发，当前保留扩展位，不封死。 | 不把“只有财务单据上传才自动重算”写成长期规则。 | 本轮提醒结果由 order 数字主导，但未来触发源仍需留出口。 |
| 2026-03-23 | 管理员手动关闭 / 恢复提醒本轮只预留后端 payload 埋口，不新增完整面板，也不新增第三种公开状态。 | 不在当前 phase 顺手扩 UI 和状态机。 | 先把最小可保留位埋好，避免把 phase-2 范围拉炸。 |
| 2026-03-23 | 提醒判定正式改为 **按行执行**：一条 `NormalizedRecord(order)` 对应一条提醒判断。 | 替换掉“先并组再用 winner 定提醒”的旧口径。 | 实际样本已证明并组 winner 会把本该报警的行覆盖掉，导致漏报。 |
| 2026-03-23 | `alert_key` 改为 `alert_type + line_key`，同一业务行重传时按最新行覆盖，旧行只保留审计记录。 | 不再用 `alert_type + group_key` 承担行级生命周期。 | 让“同一行最新有效记录生效”在提醒层可追踪、可重算、可消警。 |
| 2026-03-23 | `match_group` 用途收敛为展示/关联，不再参与提醒触发决策。 | 不再允许组级 winner 直接决定提醒是否触发。 | 彻底切断“展示分组逻辑”和“报警判定逻辑”的耦合。 |
| 2026-03-23 | order 映射补充别名：`商品编码 -> item_code`、`商品名称 -> item_name`。 | 修复旧映射只识别“料号/品名”导致 item 字段空值的问题。 | 防止多商品行在同订单下因 item 为空被错误并组。 |
| 2026-03-23 | 预警文案统一由后端生成：短版写入 `Alert.message`，长版写入 `payload.message_long`。 | 不再由页面临时拼接或保留技术口径提示语。 | 让页面、导出、接口口径一致，先把“人话可读”做成后端标准输出。 |
| 2026-03-23 | 发票提醒短版措辞固定为“距最近出库已〔X〕天”；金额字段有值则展示，无值走降级文案“金额暂无”。 | 不再沿用“已出库X天”的旧短语，也不再硬填金额。 | 更贴合当前规则口径并避免金额缺失时误导。 |
| 2026-03-24 | 跨 job 生命周期回收正式补齐：同一业务行被新 job 重新评估后，按 `alert_type + line_key` 自动把其它 job 的旧 `open` 预警转 `resolved`。 | 不再仅限同 job 内回收旧预警。 | 修复“旧批次仍挂未解除、新批次已不命中”的状态滞留问题，确保最新结果主导。 |
| 2026-03-25 | 当前 order 行新增内部状态 `completed_skip_scan`：当 `quantity > 0`、`executed_shipped_qty = quantity`、`uninvoiced_qty = 0` 且不是明显异常/脏数据时，后续重点扫描直接跳过。 | 不再只把“事实上已完成”的行留在普通扫描链里被重复评估。 | 先把“已完成可跳过扫描”正式编码进链路，但不扩成新的公开状态机，也不改变现有提醒生命周期。 |
| 2026-03-25 | 审计页查看 `scan_state` 采用最小改法：不新开页面，只在现有文件操作列补“查看归一化记录”，并在右侧现有预览区展示。 | 不做复杂新页面，也不把归一化明细藏在数据库里只能查 SQL。 | 让月总能在现有审计页直接点着看 `core.scan_state`、关键判断字段和跳过原因。 |

| 2026-03-27 | `分录行号` 正式接入 order 行 payload，并升级为行业务主身份的优先字段；只对新上传数据生效。 | 不再只靠 `customer_order_no + item_code/item_name` 认定“同一业务行”。 | 新 Excel 已稳定带出 `分录行号`，这比商品名称/编码更适合区分同一订单里的具体行。 |
