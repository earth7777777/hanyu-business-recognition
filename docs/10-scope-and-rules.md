## 2. 业务规则

### 2.1 上传与单据类型规则
- 上传时必须由用户手动选择单据类型，当前固定为 4 类：
  - 合同订单 -> `order`
  - 发货单 -> `shipment`
  - 付款通知单 -> `payment_notice`
  - 发票 -> `invoice`
- 当前上传入口选择的是**单据类型**，不是文件格式。Excel、PDF、图片属于文件形式，不是当前入口类型值。
- 当前阶段不允许再走“默认第一项就是 order 的静默上传”。
- 如果用户未选择单据类型，不允许上传。

### 2.2 Excel 导入规则
- 当前系统允许 Excel 中存在很多无关列、杂项列、垃圾列；系统应**抓关键列、忽略无关列**，而不是要求用户先把表清洗到极致。
- 对 `document_type=order`，当前必须启用**有效订单行门禁**，避免半空垃圾行进入数据库。
- 当前订单有效行判断走保守规则：
  - 至少满足一类“身份锚点”；
  - 且至少满足一类“业务信号”；
  - 两边都成立，才视为有效订单行并入库。
- 当前规则下，`parsed_count` 和 `/records` 的返回结果，应反映过滤后的真实有效行，而不是原始 Excel 全部行数。

### 2.3 关键字段入库规则
- 当前订单关键字段先补强进现有归一化结果，不做大规模数据库重构。
- 当前字段主要落在 `normalized_records.payload_json` 中，并按两层保存：
  - `payload.core.*`：给系统判断和后续提醒逻辑使用的规范值；
  - `payload.ext.*_raw`：保留原始文本，方便审计和回查。
- 当前应优先保证以下字段在 `core` 层可判断：
  - `entry_line_no`
  - `order_closed`
  - `line_closed`
  - `latest_outbound_date`
  - `order_outbound_status`
  - `line_outbound_status`
  - `executed_shipped_qty`
  - `invoiced_qty`
  - `uninvoiced_qty`
  - `line_invoice_status`
- 当前应同时保留原始文本，例如：
  - `entry_line_no_raw`
  - `order_closed_raw`
  - `line_closed_raw`
  - `order_outbound_status_raw`
  - `line_outbound_status_raw`
  - `line_invoice_status_raw`
  - 以及相关原始日期/数量文本。
- 针对金蝶当前真实导出习惯，下面这 `3` 个数量字段在“列已存在但单元格为空”时，当前正式按 `0` 处理：
  - `executed_shipped_qty`
  - `invoiced_qty`
  - `uninvoiced_qty`
- 这条兼容只限上述 `3` 个数量字段；不外扩到日期字段、关闭状态字段或其它业务字段。

### 2.4 关闭状态规则
- 业务上，**关闭状态、行关闭状态本身仍属于重要业务信息**，并且当前要继续真实入库、保留原始值。
- 当前要兼容的异常，不是“列在但值空着”，而是：**导出 Excel 时，整列没有被带出来**。
- 所以当前字段处理规则仍是：
  - **有关闭列**：按真实值归一化并入库；
  - **缺关闭列**：记为 `null/未知`；
  - **不允许把缺列硬猜成未关闭**。
- 但截至当前生效口径，**关闭状态只作为展示参考，不参与两条提醒是否触发的硬过滤**。

### 2.5 行开票状态规则
- 行开票状态当前必须同时保留原始文本和规范值。
- 当前至少要稳定支持这些常见归一化映射：
  - 全部开票 -> `invoiced`
  - 部分开票 -> 对应部分开票规范值
  - 未开票 -> 对应未开票规范值
- 当前如果原始值已写入但规范值为空，视为第一步未收口。

### 2.5.1 出库状态规则
- 当前销售订单里的 `出库状态 / 行出库状态` 要真实入库，并同时保留规范值和原始文本。
- `出库状态` 落到 `payload.core.order_outbound_status`，原始值落到 `payload.ext.order_outbound_status_raw`。
- `行出库状态` 落到 `payload.core.line_outbound_status`，原始值落到 `payload.ext.line_outbound_status_raw`。
- 当前规范值固定为：
  - `全部出库` -> `fully_outbound`
  - `部分出库` -> `partially_outbound`
  - `未出库` -> `not_outbound`
- 缺列、空值或无法识别时记为 `null/未知`，不允许凭数量字段硬猜成已出库。
- `行出库状态 = 全部出库` 是后续 `超60天没开票` 行级催票规则的重要事实源；具体提醒触发条件归 `phase-9` 处理。

### 2.6 重复与删除规则
- 当前不再保留前台“查看重复来源”入口。
- 当前文件级“重复风险 / 重复来源”不再作为主操作入口；前台主要保留“自动清理重复数”等留痕。
- 后端 `/v1/admin/files/{file_id}/duplicates` 旧接口也已下线；不再保留无前台入口的重复来源查询口。
- 当前 `order` 记录级已新增一条窄范围规则：当且仅当**严格新规则命中**（带 `entry_line_no`）、且“同一个人 + 四个状态字段全一致”时，新上传的重复记录会被自动删除，不再保留 `duplicate_shadow`。
- 这条自动删除只限**确定重复**：
  - 命中 `strict_line_no`
  - `change_type = duplicate`
  - 只删新进来的重复记录
- 当前 **legacy_fallback / legacy_bridge** 仍不自动删；没有分录行号或证据不够扎实时，只保留人工核对路径。
- 当前 `order` 已补一版**轻量漂移防护**，进入待复核区的第一版条件固定为两条：
  - 这 `9` 列里只要缺任意一列，就进入待复核区：
    - `customer_order_no`
    - `entry_line_no`
    - `biz_date`
    - `item_name`
    - `item_code`
    - `latest_outbound_date`
    - `executed_shipped_qty`
    - `invoiced_qty`
    - `uninvoiced_qty`
  - 认人的这 `5` 列里只要任意一个值为空，也进入待复核区：
    - `customer_order_no`
    - `entry_line_no`
    - `biz_date`
    - `item_name`
    - `item_code`
- 当前这版漂移防护只负责“拦进待复核区”，不直接判死刑；对应原因会写成：
  - `pending_review_missing_required_columns:*`
  - `pending_review_missing_identity_values:*`
- 当前只要命中 `legacy_fallback / legacy_bridge` 且找到了候选记录，不论它表现为重复还是更新，都会先冻结成 `review_pending` 并进入审计视角里的 **待复核区**；它们不混进回收站，也不混进已归档。
- 当前进入待复核区的记录一律先冻结：不抢当前有效、不改变旧版状态、不关闭或新开现有预警，也不通过常规入口放回当前数据；即使系统还能认出它对应哪条主记录，也只用于后续“对比主记录”动作，不提前影响主链。
- 当前对“严格命中的确定重复”已补最小留痕：
  - 文件级保留 `auto_deleted_duplicate_count`；
  - 批次汇总直接显示“自动清理重复数”。
- 当前待复核区按“两条轴”展示：
  - `复核状态`：待复核中 / 历史兼容状态；
  - `生效状态`：当前有效 / 仅保留，不生效 / 失效旧版。
- 当前列表直接可见的最小对账项已补：
  - 批次汇总显示：`待复核记录数 / 复核放回数 / 自动清理重复数`；
  - 文件列表显示：`待复核数 / 复核放回数 / 自动清理重复数`；
  - 记录列表直接显示：`状态标签 / 复核状态 / 生效状态`。
- 当前待复核区保留的可见动作是 3 个：
  - 可直接对比主记录；
  - `放入回收站`：按删除线进入回收站，后续是否彻底删除由回收站统一处理；
  - `放入特殊情况区`：按人工完成区逻辑转入特殊情况区，不再参与当前扫描。
- 当前待复核区不再保留人工“确认重复并删除”这种直接判断口；若需要删，统一走回收站。
- 当前待复核区两类人工处置动作都可直接执行，原因继续只是可选备注；若填写则继续记入文件 `meta_json.review_queue_actions` 留痕。
- 当前审计区的**人工生命周期主操作**正式只落在**记录**这一层：
  - `放入回收站`
  - `放入特殊情况区`
  - `放回待复核区`
  - `回到 job列表`
  - `恢复`
  - `预览删除影响 / 预览硬删除 / 执行硬删除`
- 当前**文件**在审计区只保留“归属 + 查看”职责：
  - 查看原文件
  - 下载
  - 查看归一化记录
  - 作为记录所属文件 / 所属批次的留痕
- 当前不再把文件当作人工生命周期主操作对象，避免出现“记录已回待复核、文件仍在回收站”这类分离状态。
- 当前底层仍保留**文件 / 记录双层软删除能力**，但审计区的人工主操作口径已收为**记录主操作**；文件不再作为人工生命周期主操作对象。
- 当前“显示已删除文件”只控制展示口径，不触发 Normalize / Match / Alert 重算。
- 当前已补“自动区 / 人工区删进回收站后的恢复规则”：
  - 从 `已归档` 删进回收站的对象，恢复后回 `已归档`；
  - 从 `待复核区` 删进回收站的对象，恢复后回 `待复核区`；
  - 从 `特殊情况区` 删进回收站的对象，第一次恢复后回 `特殊情况区`；
  - `已归档 / 待复核区` 这两类自动区对象，不回 `当前数据`，也不回 `job列表` 主链；
  - `特殊情况区` 这种人工区对象，如果它原来来自 `待复核区`，则允许直接“放回待复核区”；
  - 其它 `特殊情况区` 人工对象，仍允许手动“回到 job列表”，并重新参与扫描和预警；
  - 回到 `job列表` 后仍按原上传时间参与判断，不能按恢复时间抢当前权利。
- 当前恢复与特殊情况区流转都要求把旧删除痕迹清干净：
  - 恢复回 `当前数据 / 待复核区 / 特殊情况区 / 已归档` 后，不允许继续残留 `deleted_at / delete_origin` 这类旧删除状态；
  - 否则启动时的生命周期回填会误把对象重新纠成回收站或归档。
- 当前审计区所有“放入回收站 / 硬删除 / 待复核删重 / 放入特殊情况”动作都不再强制输入短语或原因，改为按钮直达；相关输入仅保留为可选备注。
- 当前回收站里的**硬删除**必须先做一次 `预览硬删除`：
  - 没先预览，不允许直接执行真正删除；
  - 预览通过后，才允许点 `执行硬删除`；
  - 这道拦截只为防误删，不改变回收站来源和恢复规则。
- 当前审计页按钮改为按审计视角分别显示，不再长期摆一排通用按钮：
  - `待复核区`：查看待复核原因 / 放入回收站 / 放入特殊情况区；
  - `已归档`：放入回收站；
  - `特殊情况区`：放入回收站 / （来源待复核时）放回待复核区 / （其它来源时）回到 job列表；
  - `回收站`：恢复 / 预览硬删除 / 执行硬删除。

### 2.7 当前提醒逻辑规则
- 当前提醒主目标仍是两条：
  - 临近交期未发货；
  - 发货后两个月未开票。
- 当前“发货后未开票”这条提醒的默认业务阈值，明确锁定为 **出库后 60 天**，并按 **大于等于 60 天** 触发。
- 当前两条提醒都按 **order 行硬数字** 判断，不再依赖付款通知单 / 正式发票 / 发货单去硬改结果。
- 当前正式生效的两条提醒规则是：
  - **临近交期未发货**：仅当 `quantity != executed_shipped_qty` 且 `due_date` 进入 `due_before_ship_days` 提醒窗口时触发。
  - **出库后 60 天未开票**：仅当 `executed_shipped_qty > 0`、`latest_outbound_date` 距今 `>= 60` 天、且 `uninvoiced_qty` 非空且 `> 0` 时触发。
- 当前 `order_closed / line_closed` 仍会随结果返回，但仅作展示参考，不作为提醒拦截门。
- 当前两条提醒文案由后端统一生成人话版本：
  - `Alert.message` 为短版（页面现有 message 列直接展示）；
  - `payload.message_long` 为长版（用于详情与后续扩展）。
- 当前发票提醒短版固定使用“距最近出库已〔X〕天”口径；金额字段有值就展示，缺值走“金额暂无”降级文案。
- 当前提醒结果由 **order 数字主导**：
  - order 更新后应重算；
  - `shipment / payment_notice / invoice` 当前不是提醒结果的硬判断依据；
  - 是否让这些单据在后续作为更多重算触发源，当前保留扩展位，不在本轮封死。
- 当前提醒判定粒度已经切到**行级**：一条 `normalized_records(order)` 对应一条提醒判定，不允许再用组级 winner 覆盖整组行结果。
- 当前同一业务行多次上传时，系统按 `line_key` 做“最新有效行覆盖”，旧记录保留审计但不再主导提醒。
- 当前 `line_key` 的 order 行主身份已升级为：
  - 优先 `customer + customer_order_no + entry_line_no`
  - 没有 `entry_line_no` 时，再回退到 `item_code / item_name / source_row`
- 当前同一业务行在新 job 到来后，会按 `alert_type + line_key` 自动回收其它 job 的旧 `open` 预警；旧预警转 `resolved` 并写入 `resolved_task_id / superseded_by_job_id / resolution_reason` 留痕。
- 当前 `match_group` 继续保留，但只用于展示与关联追踪，不再作为提醒是否触发的决策依据。
- 当前 order 行会在归一化阶段额外计算一个内部扫描状态 `scan_state`：
  - 当 `quantity > 0`、`executed_shipped_qty = quantity`、且“行未开票数量 = 0 或该单元格为空（仅对这一列按 0 处理）”，并且该行不是明显异常/脏数据时，记为 `completed_skip_scan`；
  - 该状态只表示“这行当前可跳过后续重点扫描”，不是永久关闭，不删记录，也不替代现有 `open / resolved` 生命周期。
- 当前提醒链已显式接入 `completed_skip_scan`：
  - 命中该状态的 order 行，不再进入“临近交期未发货”和“出库后 60 天未开票”两条提醒判断。
- 当前 order 行已补一个稳定落库字段：`order_unshipped_qty`。
  - 含义固定为：`quantity - executed_shipped_qty`；
  - 若结果小于 `0`，当前夹到 `0`；
  - 只表达“这一行肯定未发货数量”，不等同于金蝶里的其它执行类字段。
- 当前自动归档只认“发齐且开齐”这条业务真值：
  - `行已执行已出库数量 = 数量`
  - `行已开票数量 = 数量`
- 当前不再使用“建议多少天后归档”这类时间口径去判断是否归档。
- 当前自动归档现在分 `自动挡 / 手动挡` 两档：
  - `自动挡`：仍由现有编排链自动触发；
  - `手动挡`：编排链不再自动真归档，改由月总在运行健康看板里手动走。
- 当前手动挡里的归档必须再拆两步：
  - 先 `试运行自动归档`
  - 再 `正式执行自动归档`
  - 且正式执行前必须基于刚才那次新鲜试运行结果，不能跳过预看直接真归档。
- 当前运营状态区里的“最近归档执行 / 最近归档结果 / 归档执行错误”应反映**真实最近一次正式归档结果**，不是只留配置壳子。
- 当前运营状态区里的“最近上传 / 最近任务”也应按**全局真实最新时间**取值：
  - 最近上传看最近一次真实文件上传，不因该文件后来已归档就丢失；
  - 最近任务看最近一次真实任务更新时间，不靠批次列表里“第一个有值”的碰运气口径。
- 当前不再把“取消归档”当正常操作入口：
  - 已归档对象留在完成区，不直接放回当前数据；
  - 若后续发现归档有误，应按异常纠错单独处理，不走页面常规按钮。
- 当前待复核区也不再保留“放回当前数据”的常规回退入口：
  - 不再提供“确认不是重复，仅保留”；
  - 不再提供“确认不是重复，设为当前有效”；
  - 不再提供“确认重复并删除”；
  - 当前待复核区只保留“放入回收站”与“放入特殊情况区”两条人工处置线，并保留“查看待复核原因”看板。
  - 当前“查看待复核原因”只展示：
    - 主原因；
    - 具体缺列 / 认人字段空值；
    - 基础信息（文件名 / 源行号 / 记录ID）；
  - 不再把“主记录对比 / 认人字段对比 / 认状态字段对比”作为当前阶段主内容。
- 当前待复核区的文件视角也必须直接暴露该批次文件：
  - 可直接点中文件；
  - 点后按文件级目标执行“查看归一化记录 / 预览原文件 / 下载 / 放入回收站”；
  - 不应再逼用户切回其它审计视角绕操作。
- 当前待复核区右侧“当前视角对象列表”也必须同时暴露：
  - `文件对象`

### 2.9 超60天没开票四阶段升级规则
- 当前 `超60天没开票` 新一轮升级拆成四张 plan：
  - `plans/phase-8-超60天没开票数据字段与云端数据结构.md`：管 `出库状态 / 行出库状态` 进入系统、payload/config 结构和云端数据事实；
  - `plans/phase-9-超60天没开票提醒规则升级.md`：管提醒触发条件、管理员规则开关和提醒 payload；
  - `plans/phase-10-超60天没开票HTML下载与打印.md`：管老板娘看的 HTML 下载文件、客户/订单/产品结构、手机查看和 A4 黑白打印；
  - `plans/phase-11-超60天没开票发布与配置入口.md`：管下载弹窗、管理员配置入口、本地验收后同步阿里云和云端验收。
- 当前已查明云端 `normalized_records` 没有 `order_outbound_status / line_outbound_status` 物理列，现有 order payload 也没有这两个字段。
- 当前新字段优先走 `payload_json.core/ext` 和 `config_entries.field_mappings` 升级，不默认新增物理列。
- 当前 `出库状态` 表示整张订单是否发完；当前 `行出库状态` 表示这一行产品是否发完。
- 当前业务口径固定为：
  - `行出库状态 = 全部出库`，才表示这一行产品已经发完；
  - `出库状态 = 全部出库`，才表示整张订单已经全部发完；
  - `出库状态 = 部分出库` 时，必须继续看每一行的 `行出库状态`，不能直接否定所有行。
- 当前 `超60天没开票` 默认提醒规则改为：按产品行催票。
  - 默认必须满足 `行出库状态 = 全部出库`；
  - 距最近出库日期 `>= 60` 天；
  - 还存在未开票数量 / 未开票金额；
  - 对应客户提醒没有被管理员关闭。
- 当前管理员后台应新增 `必须整单发完后才提醒` 开关：
  - 默认关闭；
  - 关闭时，一行产品发完即可按 60 天规则催这一行；
  - 打开时，还必须满足 `出库状态 = 全部出库`。
- 当前 HTML 是催票行动清单，不是完整订单报表。
- 当前 HTML 必须按客户集中展示：
  - 一个客户的所有应催订单讲完，再进入下一个客户；
  - 一张订单内的产品行必须放在同一张订单卡里，不允许散开。
- 当前只有订单里至少有一行满足应催条件，整张订单卡才出现在 HTML；没有任何应催行的订单不出现。
- 当前 HTML 客户汇总金额拆成两栏：
  - `应催金额`
  - `未发完暂不催金额`
  且汇总数字必须能在正文卡片里找到来源。
- 当前整单已发完但只开了一部分票时，卡片仍归入“整单已发完 / 应催”区域，并必须写清已开票和未开票。
- 当前整单已发完的订单里，已经开完票的产品也要列出来，但弱化显示，标清 `已开完，不用催`，且不计入应催金额。
- 当前部分发货订单里，未发完的产品可作为背景信息显示开票情况，但必须标 `先不催`，且不计入应催金额。
- 当前行已发完但未满 60 天的产品不在 HTML 里显示，避免误催。
- 当前 HTML 卡片标题顺序固定为：
  1. 客户名
  2. 单据编号
  3. 状态标签
  4. 应催金额
- 当前 HTML 打印 / 查看规则固定为：
  - 手机查看：一行 1 张卡片；
  - A4 打印：一行 2 张卡片；
  - 这里的“一行几张”指客户卡 / 订单卡这类卡片。
- 当前黑白打印优先：不使用大面积深色块，主要靠边框、分隔线、字号和字重区分层级；金额用字号和加粗突出。
- 当前 Excel 保持此前已确认的核对表方案，不跟随本次 HTML 的整单/部分发货复杂结构升级。
- 当前 Excel 仍固定分成两个工作表：
  - `客户汇总`
  - `明细清单`
  两个部分不能上下堆在同一个 sheet。
- 当前 Excel `明细清单` 字段顺序固定为：
  1. 序号
  2. 客户
  3. 单据编号
  4. 产品
  5. 未开票金额
  6. 未开票数量

  8. 已超过天数
  9. 订单数量
  10. 已出库数量

- 当前 `未开票金额` 固定用这一条产品行自己的未开票金额，必须和这一行的 `未开票数量` 对应。
- 当前下载格式固定支持：
  - Excel；
  - HTML；
  - 全部。
- 当前选择 `全部` 时，直接分别下载 Excel 与 HTML 两个独立文件，不做 zip 压缩包。
- 当前无数据时固定提示：`当前没有超60天没开票数据`，不生成空文件。
- 当前下载相关文案不使用 `未解除` 三个字。

  - 顶栏左侧为 `返回`；
  - 中间标题为 `超60天没开票`；

  - 客户排序；

- 当前本次 PWA 调整不做桌面端重排。

### 2.10 运维底座工程冻结规则
- 当前运维底座工程按 **后端先行 + 测试面板最小验证入口** 推进：
  - 先把后端托底能力做稳；
  - 测试面板只负责最小查看和最小操作；
  - 正式员工看板后置。
- 当前运维底座工程第一段最小范围固定为 4 块：
  - 运行健康看板；
  - 数据库备份与上传件备份可见性；
  - 核心运维告警；
  - 自动归档第一版。
- 当前“运行健康看板”最少要让月总直接看到：
  - 最近一次导入；
  - 最近一次任务；
  - 失败次数；
  - 待复核数；
  - 空壳批次数；
  - 解析失败数；
  - 上次数据库备份成功时间；
  - 上次上传件备份成功时间。
- 当前“备份规则”先固定为两条：
  - 数据库定时备份；
  - 上传件定时备份；
  - 并且都要能直接看见“上次成功时间 / 最近状态 / 是否超时”。
- 当前第一段先收的告警类型固定为：
  - 解析失败；
  - 待复核激增；
  - 批次长期失败；
  - 数据库备份失败或超时；
  - 上传件备份失败或超时；
  - 归档任务失败或超时。
- 当前这些运维阈值不在规则正文里写死数字，正式口径改为：
  - 做成配置项；
  - 页面可见；
  - 默认值可验；
  - 后续可调。
- 当前自动归档第一版只允许处理：
  - 已完结；
  - 且长期不参与当前扫描；
  - 的数据。
- 当前自动归档第一版必须拆成两步：
  - `先试运行`
  - `再正式执行`
  - 不允许一上来直接真归档。
- 当前手动挡下，没先做过新鲜的 `试运行` 时，不允许直接点 `正式执行`。
- 当前不恢复“取消归档”按钮和常规程序入口；若后续发现归档有误，仍走单独纠错，不走常规悔步。
- 当前第二段增强内容已冻结，但明确后置：
  - 慢查询识别；
  - 日志留存与自动清理；
  - 恢复演练；
  - 归档后的查询入口。
- 当前月总日常使用这块的预期方式固定为：
  - 平时主要看“运营状态区”的红黄绿和数字；
  - 出现异常时，只做“看原因 / 决定是否人工处理 / 必要时恢复备份”这三类动作；
  - 不应把“需要进数据库翻半天”当成常规使用方式。

### 2.11 页面B永创手稿提醒第一阶段规则
- 当前已确认新增阶段为 `phase-12-页面B永创手稿提醒标准与入口`。
- 页面 A 继续定义为金蝶提醒展示页：
  - 只展示金蝶数据生成的 `发货超过 60 天未开票`；
  - 保持干净、只读、无互动；
  - 页面 A 数据错误时，回金蝶源头修正，再重新导入/刷新；
  - 不在 A 页面或展示层直接改数据。
- 页面 B 第一阶段只做永创手稿提醒：

## 3. 边界和明确不做什么
- 当前不把 **jpg/png 直接识别、PDF 直接识别、OCR 能力** 当成上线主线。
- 当前不把“自动下载金蝶数据”作为必须先完成的前提。当前主线仍是：**人工从金蝶导出标准 Excel，再由系统导入**。
- 当前不做最终员工正式页面，不做完整角色系统，不做最终生产级 UI 包装。
- 当前不做 Job 级删除，不做批量物理删除。
- 当前不做重复文件自动删除。
- 当前不要求用户先把 Excel 清理成只剩关键列才允许导入。
- 当前不把预计交货日期直接当成关闭状态的替代品。
- 当前不允许因为关闭列缺失，就默认认定订单/订单行为“未关闭”。
- 当前不做大规模数据库重构成全新订单主表/明细表体系，先沿现有链路补强。
- 当前 `超60天没开票` 下载升级不改成“整单发齐后才算 60 天”，不把下载排序扩散到页面列表，不做 zip，不做桌面端重排。
- 当前 `phase-12` 不允许把老婆手稿数据并入页面 A 的金蝶提醒链路，不允许复用龙虾旧入口承载手稿上传，不允许把手稿清洗小软件混进本仓库当前软件代码里。

## 4. 例外、风险与禁止事项
- **禁止把缺关闭列猜成未关闭。** 这是当前字段归一化层必须守住的底线。
- **禁止把关闭状态直接当提醒硬拦截门。** 当前真实金蝶数据里已经出现“行未开票数量 > 0，但行关闭状态 = 已关闭”的场景，机械拦截会漏报。
- **禁止为了省事跳过半空行过滤。** 否则 Excel 一脏，提醒链就会被污染。
- **禁止把测试页当前能用，误当成最终员工工作台已完成。**
- **禁止把 `completed_skip_scan` 误当成永久关闭或物理删除。** 它只是一种当前跳过重点扫描的内部状态。
- 当前阶段的主要风险不是“吃不进去”，而是：
  - Excel 列名轻微变化导致映射失准；
  - 半空行、杂项行混入，污染有效记录；
  - 同一订单后续补传新 Excel 时，如果不按最新有效记录重算，旧提醒会继续挂着；
  - 关闭状态虽然已入库，但如果被误当成绝对拦截门，会把真实未开票场景漏掉。
