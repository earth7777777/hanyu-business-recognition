# 验收标准

## 1. 用户如何检查
- 先启动后端、前端和 MariaDB。
- 用真实业务文件做最小整链检查，至少覆盖这四类：
  - 订单
  - 发货单
  - 付款通知单
  - 正式发票
- 检查顺序按下面做：
  1. 上传订单文件，确认系统能识别、入库，不报类型错误。
  2. 用带行级硬数字的 order Excel 验证两条核心预警：
     - `quantity != executed_shipped_qty` 且进入提醒窗口时，触发“快到交期未发货”。
     - `executed_shipped_qty > 0`、`latest_outbound_date >= 60 天`、且 `uninvoiced_qty > 0` 时，触发“出库后 60 天未开票”。
  3. 在提醒已打开后，单独补传 `payment_notice / invoice / shipment`，但不更新 order 数字，确认提醒结果不会仅因这些单据本身被硬改。
  4. 再补一份新的 order Excel，更新同一订单同一行的 `uninvoiced_qty=0` 或 `executed_shipped_qty=quantity`，确认系统会自动重算并更新原提醒状态。
  5. 上传一条“`quantity > 0`、`executed_shipped_qty = quantity`、`uninvoiced_qty = 0`”的有效 order 行，确认该行不会继续进入两条提醒判断；必要时直接查 `normalized_records.payload_json.core.scan_state = completed_skip_scan`。
     - 如果金蝶该样本把“行未开票数量=0”导成空单元格，也应按同样口径进入 `completed_skip_scan`；但仅这一列这样处理。
  6. 新建第二个 job，上传同一业务行的新 order 结果，确认跨 job 生命周期正确：
     - 若新 job 不再命中，旧 job 的同业务行预警应自动 `resolved`；
     - 若新 job 仍命中，旧 job 也应自动 `resolved`，只保留新 job 为 `open`。
  7. 故意传一个明显错类型的文件，确认高置信错分会被拦截，不会直接入库。
  8. 用《引出列表_销售订单_20260323211238.xlsx》复验“按行判定”：
     - 解析记录数应为 3；
     - `ship_after_no_finance` 未解除预警应为 2（第 1 行和第 2 行）；
     - 第 3 行不触发；
     - 每条预警 payload 可定位 `source_row / record_id`。
  9. 在“预警结果”区域刷新后，确认 `message` 已是人话短版：
     - 发票提醒包含“距最近出库已〔X〕天”；
     - 金额有值时显示金额；
     - 金额缺失时短版不硬填金额，长版 `payload.message_long` 出现“金额暂无”。
  10. 抽查任一发货提醒，确认短版包含：单据编号、商品名称/编码、预计交货日期、订单数量、已执行已出库数量、未发数量。
  11. 在审计页选中当前文件后，点“查看归一化记录”，确认右侧能直接看到：
     - `core.scan_state`
     - 单据编号 / 商品名称 / 商品编码
     - 数量 / 行已执行已出库数量 / 行未开票数量
     - “为什么跳过扫描 / 为什么仍参与提醒”的说明。
  12. 在“关联结果摘要”里确认三项统计：
     - 总记录数 = 已进入归一化处理的记录数；
     - 跳过扫描数 = `scan_state = completed_skip_scan` 的记录数；
     - 实际扫描数 = 总记录数 - 跳过扫描数。
  13. 用带“分录行号”的新 order Excel 验：
     - 审计页归一化记录里能看到 `entry_line_no`
     - 同一单据下不同 `分录行号` 的两行，不会再因为商品相同被当成同一业务行
     - 同一 `单据编号 + 分录行号` 后续重传时，旧预警按最新结果更新。
  14. 对金蝶当前这 3 个数量字段额外抽验空值兼容：
      - `行已执行已出库数量`
      - `行已开票数量`
      - `行未开票数量`
      - 当列已存在但单元格为空时，系统应按 `0` 处理，不应把它们继续当成未知。
  15. 对“带分录行号且完全重复”的 order 重传额外抽验：
      - 第二次重传后，不应再留下新的 `duplicate_shadow`；
      - 新上传重复记录应被自动删除；
      - 原主记录继续保持 `current`；
      - 如果第三次再上传状态变化版，仍应正常判成 `update`。
  16. 对漂移防护第一版额外抽验：
      - 只要这 `9` 列里缺任意一列，当前上传应进入待复核区；
      - 认人的这 `5` 列里只要任意一个值为空，当前上传也应进入待复核区；
      - 进入待复核区后，不应提前影响现有当前有效记录和现有预警。
  17. 对 `已归档` 对象额外抽验：
      - 放入回收站时，管理员无需精确输入确认短语；
      - 从回收站恢复后，应回 `已归档`；
      - 不回 `当前数据`，不参与扫描，不新开预警。
  18. 对 `待复核区` 对象额外抽验：
      - 放入回收站时，管理员无需精确输入确认短语；
      - 从回收站恢复后，应回 `待复核区`；
      - 不回 `当前数据`，也不应重新混进顶部“当前数据”视角。
  18. 对 `特殊情况区` 对象额外抽验：
      - 放入回收站时，管理员无需精确输入确认短语；
      - 从回收站恢复后，第一次应回 `特殊情况区`；
      - 从 `特殊情况区` 再点“回到 job列表”后，应重新参与扫描和预警；
      - 回到 `job列表` 时，应回原文件 / 原批次，并继续按原上传时间参与裁决。
- 当前真实业务验证，优先用这几种场景：
  - 有交期、`quantity != executed_shipped_qty` 的订单
  - `latest_outbound_date` 距今 59 天、`uninvoiced_qty > 0` 的订单行
  - `latest_outbound_date` 距今 60 天、`uninvoiced_qty > 0` 的订单行
  - 同一业务键补传新 order Excel 后更新提醒的场景
  - 关闭状态为“已关闭”但 `uninvoiced_qty > 0` 的真实订单行
  - 同一张订单含多行商品的场景

## 2. 通过标准
- 以下条件同时满足，才算当前阶段通过：
  1. 人工上传链路能跑通：上传 → 识别 / 判型 → 入库 → 匹配 → 预警 / 消警。
  2. 外部工具 intake 链路能跑通：外部投喂文件 / 取结果不破坏主链。
  3. 四类文件能分别进入正确业务位置：
     - 订单
     - 发货单
     - 付款通知单
     - 正式发票
  4. 高置信错分文件会被拦截，不会静默入错库。
  5. “快到交期未发货”预警能打中。
  6. “发货超过阈值未开票”预警能打中。
  7. 单独补传 `payment_notice / invoice / shipment`，在不更新 order 数字时，不会把提醒结果硬改掉。
  8. 同一业务键补传新 order Excel 后，系统会自动重算，并让原提醒更新或变成 `resolved`。
  9. `order_closed / line_closed` 当前只作展示参考，不会把本应命中的提醒硬拦掉。
  10. 预警不是只会新建；系统能保留最小生命周期，至少区分 `open / resolved`。
  11. 预警 payload 已带出管理员手动关闭 / 恢复的保留字段，且后续重算不会把这些字段冲掉。
  12. 自动化测试保持通过。
  13. 同一订单多商品行场景下，提醒按行独立判定；不得再出现“前两行被第 3 行 winner 覆盖后整体不报”的情况。
  14. 两类提醒的短版/长版文案字段完整：`Alert.message` 为短版，`payload.message_long` 为长版，并与当前规则口径一致。
  15. 同一业务行跨 job 重传时，旧 job 的同键 `open` 预警会自动转 `resolved`，新 job 只保留最新状态（命中则 `open`，不命中则无 open）。
  16. 对“已完整发货且未开票数量为 0”的有效 order 行，系统会写出内部 `completed_skip_scan` 状态，并在提醒判断前显式跳过这类行。
  17. 对“行未开票数量”这一列，金蝶 Excel 若用空单元格表示 0，系统只在 `completed_skip_scan` 判断里把它按 0 处理；其它空值口径不变。
  18. 审计页可直接查看归一化记录，且不需要另开新页面或查 SQL 才能看到 `core.scan_state`。
  18.1. 审计区人工生命周期操作应只对**记录**开放：
      - 点文件 ID / 文件名时，只能查看文件与归一化记录，不应直接露出回收站 / 特殊情况 / 回退 / 恢复 / 硬删除按钮；
      - 只有点中“记录目标”后，才应出现这些人工生命周期按钮。
  19. 对带 `分录行号` 的新 Excel，系统会把它写入 `payload_json.core.entry_line_no / ext.entry_line_no_raw`，并优先用于生成 `line_key`。
  20. 对 `executed_shipped_qty / invoiced_qty / uninvoiced_qty`，若金蝶导出列存在但单元格为空，系统会按 `0` 参与当前业务判断；这条兼容不外扩到日期字段。
  21. 对 order 行，系统会稳定落库 `order_unshipped_qty`，并按 `quantity - executed_shipped_qty` 计算；若源数据异常导致结果为负，数据库中按 `0` 保存。
  22. 对带 `entry_line_no` 的确定重复，系统会自动删除新上传重复记录；但对 `legacy_fallback / legacy_bridge` 不自动删，避免误伤无分录行号样本。
  23. 对漂移防护第一版，系统应执行轻量拦截：
      - `order` 这 `9` 列缺任意一列 -> 进入待复核区；
      - 认人的 `5` 列任意值为空 -> 进入待复核区；
      - 不得把“认状态 4 列空值”一律当成漂移异常。
  24. 对 `legacy_fallback / legacy_bridge` 命中候选后留下来的 `review_pending` 记录，审计视角里应能在“待复核区”单独看到，且不混进回收站 / 已归档。
  25. 进入待复核区的记录必须先冻结：
      - 不抢当前有效；
      - 不改变旧版状态；
      - 不提前关闭或新开现有预警；
      - 不通过常规入口放回当前数据。
  26. 即使记录因为漂移防护进了待复核区，只要系统还能识别出它对应的主记录，也应支持：
      - 待复核区“对比主记录”仍能看到并排对比；
      - 人工仍能基于对比结果决定“放入回收站”或“放入特殊情况区”；
      - 不再通过常规入口直接放回当前数据，也不再在待复核区里直接做“确认重复并删除”。
  27. 对“严格重复自动删”，系统应保留最小计数留痕：
      - 文件详情可看到该文件自动清掉了几条确定重复；
      - 批次汇总可看到“自动清理重复数”；
      - Job/文件列表可分别看到 `待复核记录数 / 复核放回数` 与 `待复核数 / 复核放回数`。
  28. 对待复核记录，系统应支持：
      - 查看它和主记录的并排对比；
      - `放入回收站`；
      - `放入特殊情况区`；
      - 不再保留 `确认重复并删除 / 确认不是重复，仅保留 / 确认不是重复，设为当前有效` 这三类旧动作；
      - 上述动作的原因输入仅作可选备注，不应阻塞执行。
  29. 记录列表应直接显示：
      - `状态标签`；
      - `复核状态`；
      - `生效状态`。
  30. 对 `已归档 / 待复核区` 这两类自动区对象，从回收站恢复后必须回原区；不得误回 `当前数据`，不得重新进入扫描主链。
  31. 对 `特殊情况区` 这类人工区对象，从回收站恢复后必须先回 `特殊情况区`；只有再手动“回到 job列表”时，才重新进入扫描主链。
  32. 审计区里的“放入回收站”对文件/记录都应支持不填确认短语直接执行；确认短语输入框仅作可选备注。
  33. 审计区里的“硬删除”在对象已在回收站时，也应支持不填确认短语直接执行。
  34. 放入特殊情况区应支持不选固定原因直接执行；未填写时后端应默认落 `其他特殊完成`，备注可选。
  35. `data_retention_policy` 中不应再保留 `archive_recommended_after_days` 这类“建议归档天数”旧字段；自动归档只按“发齐且开齐”判断。
  36. 当前前端页面打开后，`后端地址` 输入框应默认按当前入口自动推断：
      - 本地 `5173` 开发态继续带出 `http://当前主机:8000/v1`
      - 云上经单入口反向代理时，默认直接走同源 `/v1`
      - 不需要每次手改成当次 WSL IP，也不需要云上手工补 `:8000`
  37. 顶部“批次汇总”应有单独“刷新批次汇总”按钮；手动修改 `后端地址` 后，顶部批次汇总、审计列表、运营状态都应自动重拉一次，而不是继续挂着旧报错。
  38. 审计页不应再出现“取消归档”按钮；`/v1/admin/files/{file_id}/unarchive` 与 `/v1/admin/records/{record_id}/unarchive` 也不应再作为有效常规入口存在。
  36. 当现有编排链自动归档了符合条件的记录后，`operations_runtime_status.archive_run` 必须被真实更新：
      - `last_status` 为本次真实结果；
      - `last_run_at` 为本次真实执行时间；
      - `last_archived_file_count / last_archived_record_count` 为本次真实归档数量；
      - 成功时 `last_error` 清空，失败时写入真实错误。
  37. 管理员查看 `/v1/admin/operations/summary` 时，“最近归档执行 / 最近归档结果 / 归档执行错误”必须与最近一次自动归档真实回写值一致。
  38. 管理员查看 `/v1/admin/operations/summary` 时，“最近上传”必须反映全局最近一次真实文件上传；即使该文件随后已自动归档，也不能退回显示更早的一条 active 文件。
  39. 管理员查看 `/v1/admin/operations/summary` 时，“最近任务”必须反映全局最近一次真实任务更新时间，不得靠批次汇总列表里“第一个有值”的条目碰运气。
  40. 顶部“批次汇总”应保留原有 `批次视角`，并额外提供独立的 `区域视角`，顺序固定为：
      - `当前数据`
      - `待复核区`
      - `已归档`
      - `特殊情况区`
      - `回收站`
  41. 顶部“批次汇总”中，`区域视角` 只影响顶部 job 列表自身；切换到不同区域后，应只显示该区域有对象的 job。
  42. `当前数据` 视角下，空壳 job 仍可在 `全部批次` 中看到；若同时切到 `仅非空壳批次`，则应被过滤掉。
  43. 顶部“批次汇总”应额外提供独立的 `业务视角`：`全部业务 / 未发货 / 未开票`。
  44. `未发货` 业务视角必须按 order 行口径判断：`行已执行已出库数量 != 数量`。
  45. `未开票` 业务视角必须按“已发部分是否开齐票”判断：`行已执行已出库数量 > 0` 且 `行已开票数量 != 行已执行已出库数量`。
  46. 对“还没发货，但金蝶显示行未开票数量”的样本，顶部 `未开票` 业务视角**不应**把它筛进来。
  47. 审计页在 `待复核区` 不应再出现“确认不是重复，仅保留”“确认不是重复，设为当前有效”或“确认重复并删除”这类旧入口。
  48. 旧的 `/v1/admin/review-queue/records/{record_id}/confirm-not-duplicate`、`/confirm-not-duplicate-make-current` 与 `/confirm-duplicate` 都不应再作为有效常规入口存在；直接访问时应返回 `404`。
  49. `待复核区` 记录当前只保留三项可见动作：
      - `查看待复核原因`
      - `放入回收站`
      - `放入特殊情况区`
  50. 审计页切到 `待复核区` 后，该批次的文件仍应直接可见、可点击。
  51. 在 `待复核区` 点中文件后，应能直接执行文件级动作：
      - `查看归一化记录`
      - `预览原文件`
      - `下载`
      - `放入回收站`
  52. `待复核区` 不应再逼用户先切回 `当前数据`，才能把待复核文件放入回收站。
  53. `待复核区` 的“当前视角对象列表”里，应同时看到该批次的：
      - 文件对象
      - 待复核记录对象
  54. `特殊情况区` 的文件列表和“当前视角对象列表”里，也应同时看到该批次的：
      - 文件对象
      - 特殊情况记录对象
  55. 审计页按钮应按审计视角区别显示，而不是长期摆一排通用按钮：
      - `待复核区`：查看待复核原因 / 放入回收站 / 放入特殊情况区
      - `已归档`：放入回收站
      - `特殊情况区`：放入回收站 / （来源待复核时）放回待复核区 / （其它来源时）回到 job列表
      - `回收站`：恢复 / 预览硬删除 / 预览后才允许执行硬删除
  55.1 点 `查看待复核原因` 后，面板应直接显示：
      - 主原因
      - 具体缺列 / 认人字段空值
      - 基础信息（文件名 / 源行号 / 记录ID）
      且不再显示“主记录对比 / 认人字段对比 / 认状态字段对比”。
  55.2 切到 `特殊情况区` 后，同一批次的“当前视角对象列表”里，文件应排在记录上面。
  55.3 顶部与文件列表里的“异常原因”对认人空值场景应显示 `认人字段空 / 待复核`，不应只剩 `待复核`。
  55.4 回收站里的对象如果没有先点 `预览硬删除`，直接点 `执行硬删除` 时应被拦住；做完预览后，才允许真正删除。
  56. `特殊情况区` 里的文件和记录都应支持“回到 job列表”。
  57. 从 `特殊情况区` 回到 `job列表` 后，旧记录仍按原上传时间参与裁决；若后面已有更新上传，不得因为恢复时间更晚而抢成当前有效。
  58. 对原来来自 `待复核区`、后被放进 `特殊情况区` 的文件或记录，在 `特殊情况区` 应能直接点“放回待复核区”。
  59. 点“放回待复核区”后，对象应回 `待复核区`，且顶部 `区域视角 = 当前数据` 不应把该批次混进来。
  60. 顶部 `区域视角 = 当前数据` 不应混入纯 `待复核区` 批次；但这些批次仍可在 `全部批次` 里作为上传留痕看到。
  61. 审计主操作区与文件表里不应再出现“查看重复来源 / 重复来源”按钮；但“自动清理重复数”留痕仍应继续显示。
  62. 对“待复核 -> 回收站 -> 恢复 -> 特殊情况区”这条链做回归：
      - 对象进入 `特殊情况区` 后，不能被误显示到 `已归档`
      - 刷新页面或重启后端后，仍应继续留在 `特殊情况区`
  63. 从回收站恢复回 `当前数据 / 待复核区 / 特殊情况区 / 已归档` 后，数据库里不应继续残留旧删除痕迹，避免启动回填误改生命周期。
  60. 后端 `/v1/admin/files/{file_id}/duplicates` 旧接口应返回 `404`；但文件列表与文件详情里的 `duplicate_risk`、`自动清理重复数` 仍应继续正常返回。

## 3. 页面不显示时如何核对
- 先看后端日志，确认上传、解析、入库、预警重算有没有报错。
- 再看自动化测试是否通过。
- 再直接查数据库，至少核对这几类事实：
  - 订单是否入库
  - 预警记录是否生成
  - 同一业务键补传新 order 后，原预警状态是否更新或从 `open` 变成 `resolved`
  - 预警 payload 中手动埋口字段是否仍在
  - 预警 payload 中 `source_row / record_id / line_key` 是否齐全
  - `normalized_records.payload_json.core.scan_state` 是否按条件写出 `completed_skip_scan`
- 页面看不到时，最小核对路径是：
  1. 查接口返回
  2. 查日志
  3. 查数据库
- 如果是判型问题，还要额外核对：
  - 调用方上传时传的 `document_type`
  - 后端判型结果
  - 是否命中了高置信错分拦截
  - 是否只触发了 warning

## 4. 还需要人工确认的点
- 真实订单文件里，不是每份都一定有明确交期；这类文件不能强行触发“快到交期未发货”，要人工确认样例是否真的具备触发条件。
- PDF / 图片在 OCR 差、多页混合、锚点弱时，当前可能只 warning 不强拦；要人工确认这些场景是否接受。
- 付款通知单和正式发票的真实业务识别，还需要继续用涵宇真实文件跑透；本轮它们不是提醒硬判断依据，但后续是否参与更多重算触发仍需人工确认。
- 关闭状态 / 行关闭状态当前只做展示参考；后续若要重新引入过滤，必须先证明不会漏掉“未开票数量 > 0 但行已关闭”的真实场景。
- 结果出口虽然支持自己软件页面查看，也保留外部工具分发方向，但当前仍要人工确认：
  - 管理员手机端是否足够方便查看和转发
  - 发货仓管上传页面是否足够简单、稳定、少操作

### 6.2 提醒中心怎么检查
- 首页第一屏必须先看到：
  - 标题 `今天先看这两件事`
  - 一句名字文案：`老板娘，先看今天的事` 或 `姚建锋，先看今天的事`
  - 右上角 `刷新`、`退出`
  - 两个大入口：`该发没发`、`超60天没开票`
- 首页第一屏不应直接出现：
  - 真实最急卡片
  - 客户搜索
  - 时间筛选
  - `已解除了`
- 首页不应再保留：
  - `实例 B · 第一阶段`
  - 账号大说明块
  - `今日新增提醒数`
  - `今日解除提醒数`
  - 首页 AI 大卡片
- 页面结构应固定为：`①总览页 -> ②单类速看页 -> ③完整长页 -> 详情页`
- 返回逻辑也必须固定为：始终回上一层，并保留原来的滚动位置和筛选状态。
- `该发没发` 入口检查：
  - 首页大块主数字应显示条数；
  - 小字应强调“先看已经拖了的”；
  - 点进去先到 `②单类速看页`
  - `②` 只允许看到 1 条最急主卡和 `查看更多`，不应出现筛选和 `已解除了`
  - 点 `查看更多` 后才进入 `③完整长页`
  - `③` 顶部切换固定为 `已经拖了 / 快到该发`
  - 默认先看 `已经拖了`
  - `快到该发` 固定按差 5 天开始提醒
  - 卡片必须整块可点，并直接写 `已拖X天` 或 `还有X天到期`
  - `已经拖了` 默认按拖得最久排前面；`快到该发` 默认按最先到期排前面。
- `超60天没开票` 入口检查：
  - 首页大块主数字当前显示总未开票金额
  - 小字应显示涉及客户数；如果金额不全，还应补 `部分金额暂缺`
  - 点进去也应先到 `②单类速看页`
  - `②` 只允许看到 1 个最该先看的客户和 `查看更多`，不应出现筛选和 `已解除了`
  - 点 `查看更多` 后才进入 `③完整长页`
  - `③` 顶部必须有 `按客户看 / 按单子看`
  - 默认先看 `按客户看`
  - `按客户看` 时，客户卡第一眼必须先给：客户名、总未开票金额、最久已超多少天、共几笔
  - 金额不全时，应明确显示 `部分金额暂缺`，但该客户仍应继续上榜
  - 桌面端点客户卡后，必须进入客户页；手机端点客户卡后，必须直接进入该客户最急的一笔订单详情
  - 桌面端客户页页顶固定先看：`客户名｜总金额`
  - 桌面端客户页第二行固定先看：`最久已超多少天｜共几笔`
  - 桌面端客户页下面的单子默认按“欠得多的排前面”
  - 切到 `按单子看` 后，单条卡片仍应优先把金额更大、拖得更久的提醒排前面。
- 员工侧筛选检查：
  - 不应再出现开始日期 / 截止日期
  - 客户筛选继续保留
  - 时间筛选应统一为：`不限 / 一周 / 两周 / 一个月 / 更久`
  - `客户筛选 / 时间桶 / 已解除了` 只允许出现在 `③完整长页`
  - 从首页点 `查看更多` 进入完整列表后，原筛选条件必须继续保留。
- 详情页检查：
  - 点提醒卡片后，必须单独进入详情页，而不是列表内展开
  - 顶部应先看到 `先看这一条` 和当前结论
  - 第一屏必须先给关键数字和压力，再给订单资料
  - `该发没发` 详情第一屏应先强调：拖了多久、还差多少
  - `超60天没开票` 详情第一屏应先强调：这笔还没开多少钱、已超多少天、客户共欠多少
  - `看原表内容` 必须放在页面最下面
  - 点返回后，应回到原来位置，不能跳回列表最顶部
  - 点开详情后，这条提醒不应继续显示为“新提醒 / 刚变更 / 刚解除”。
- AI 占位检查：
  - 首页/主列表同屏页面和详情页都必须看得到右下角很小的 `AI` 按钮
  - 登录页不应出现 `AI`
  - 点开后应进入单独占位页，而不是直接在当前页弹聊天框
  - 占位页应显示：
    - `AI 入口先留在这里`
    - `这一版只留一个小入口，不在首页直接弹聊天框。`
    - 后续示例文案：解释提醒、归纳客户问题、把详情和原表一起讲清楚

## 8. phase-8-超60天没开票数据字段与云端数据结构验收

### 8.1 字段入库怎么检查
- 用带 `出库状态 / 行出库状态` 的金蝶销售订单 Excel 上传。
- 验收时至少确认：
  1. `normalized_records.payload_json.core.order_outbound_status` 有规范值；
  2. `normalized_records.payload_json.core.line_outbound_status` 有规范值；
  3. `payload_json.ext.order_outbound_status_raw` 保留金蝶原始 `出库状态`；
  4. `payload_json.ext.line_outbound_status_raw` 保留金蝶原始 `行出库状态`；
  5. 管理员查看归一化记录时能直接看出“整单是否发完”和“本产品是否发完”，并用中文展示，不直接暴露英文规范值。
- 规范值至少应满足：
  - `全部出库` -> `fully_outbound`
  - `部分出库` -> `partially_outbound`
  - `未出库` -> `not_outbound`
- 老 Excel 如果缺这两列，不应被硬猜成 `全部出库`，应保留 `null/未知`。

### 8.2 云端配置怎么检查
- 云端 `config_entries.field_mappings` 应包含 `order_outbound_status / line_outbound_status` 映射。
- 本地默认配置和云端数据库配置应口径一致。
- 既有数据库配置缺少这两个字段时，初始化流程应能补齐映射。
- 不应把数据库密码、token、私钥写进项目文件、Notion 或 Git。
- 本阶段不要求改提醒触发条件；提醒规则验收归 `phase-9`。

## 9. phase-9-超60天没开票提醒规则升级验收

### 9.1 默认行级催票规则怎么检查
- 默认开关关闭时，使用下列样本验收：
  1. `行出库状态 = 全部出库`、超过 60 天、仍未开完票：应触发 `超60天没开票`；
  2. `行出库状态 != 全部出库`：即使未开票数量很大，也不应触发；
  3. 行已全部出库但未满 60 天：不应触发；
  4. 行已全部出库、超过 60 天，但已全部开票：不应触发。

### 9.2 整单发完开关怎么检查
- 管理员打开 `必须整单发完后才提醒` 后：
  1. 整单 `出库状态 = 部分出库` 时，即使某行已经全部出库，也不应触发未开票提醒；
  2. 整单 `出库状态 = 全部出库` 且产品行满足应催条件时，应触发。
- 管理员关闭该开关后：
  1. 整单 `部分出库` 但某产品行 `全部出库`，且超过 60 天未开完票，应重新触发。

### 9.3 提醒 payload 怎么检查
- `ship_after_no_finance` 的 alert payload 应带出：
  1. 整单出库状态；
  2. 行出库状态；
  3. 订单数量；
  4. 已出库数量；
  5. 已开票数量；
  6. 未开票数量；
  7. 最近出库日期；
  8. 已超过天数。

## 10. phase-10-超60天没开票HTML下载与打印验收

### 10.1 HTML 结构怎么检查
- 下载 HTML 后，直接用浏览器打开文件。
- 验收时至少确认：
  1. HTML 按客户集中，一个客户的订单讲完后才进入下一个客户；
  2. 订单卡内部能看出同一订单里的产品行关联；
  3. 没有任何应催行的订单不出现在 HTML；
  4. 订单卡标题顺序为：客户名、单据编号、状态标签、应催金额；
  5. 页面不出现 `未解除` 三个字。

### 10.2 订单卡内容怎么检查
- 整单已发完但只开了一部分票时：
  1. 卡片仍在“整单已发完 / 应催”区域；
  2. 已开票数量 / 金额和还差开票数量 / 金额都显示；
  3. 还差开票金额更醒目。
- 已经开完票的产品：
  1. 仍出现在同一订单卡里；
  2. 弱化显示；
  3. 标 `已开完，不用催`；
  4. 不计入应催金额。
- 部分发货订单：
  1. 至少有一行应催时，订单卡才出现；
  2. 已发完应催产品放在 `已发完，应该催票`；
  3. 未发完产品放在 `还没发完，先不催`；
  4. 未发完产品可显示开票情况，但必须标 `先不催`，且不计入应催金额。

### 10.3 汇总和打印怎么检查
- 客户汇总应拆成：
  1. 应催金额；
  2. 未发完暂不催金额。
- 两个金额都必须能在正文订单卡中找到来源。
- 手机宽度查看时，一行 1 张卡片。
- A4 打印预览时，一行 2 张卡片。
- 黑白打印预览中，卡片不能因为大面积色块变暗；金额主要靠字号和加粗突出。

## 12. phase-12-页面B永创手稿提醒标准与入口验收

### 12.1 管理员入口怎么检查

  4. 入口提示语显示：`只进入页面B工作台，不影响页面A（金蝶提醒）。`；
  5. 该区域能选择并上传页面 B 标准 Excel；
  6. 上传后能显示成功、失败、缺字段等导入结果。

### 12.2 标准 Excel 怎么检查
- 标准 Excel 必须包含并识别这些字段：
  1. 客户；
  2. 合同号 / 订单号；
  3. 产品；
  4. 未开数量；
  5. 未开金额；
  6. 已开数量；
  7. 已开金额；
  8. 订单时间；
  9. 来源；
  10. 状态。
- 这些字段是本阶段完整标准，不按“先少做、后补字段”验收。
- 手稿提醒的超期天数必须按 `订单时间` 计算。
- 任一字段源数据缺失时，页面显示 `缺失`，不得留空、隐藏或自行推算。

### 12.3 页面 B 汇总与客户卡怎么检查
- 打开页面 B 手稿提醒入口。
- 顶部汇总必须显示：
  1. 待催客户；
  2. 待催金额；
  3. 最久已超；
  4. 来源。
- 第一屏汇总下面必须显示客户卡片，不应直接平铺全部明细。
- 客户卡片必须显示：
  1. 客户名；
  2. 待催金额；
  3. 共几笔；
  4. 最久已超；
  5. 来源。
- 页面 B 视觉应参照页面 A，不能做成另一套后台表格风格。

### 12.4 客户详情与明细卡怎么检查
- 点击客户卡片后进入客户详情。
- 客户详情里的明细按 `订单时间` 排序。
- 明细卡字段顺序必须固定为：
  1. 合同号 / 订单号；
  2. 产品；
  3. 未开数量；
  4. 未开金额；
  5. 已开数量；
  6. 已开金额；
  7. 订单时间；
  8. 来源。
- 不得把金额放到合同号和产品之前。
- 不得把字段顺序改成后台表格式自由排列。

### 12.5 状态怎么检查
- 手稿提醒状态至少支持：
  1. `待催`；
  2. `已联系`；
  3. `不再提醒`。
- `不再提醒` 后，该记录不应继续出现在主提醒列表。
- `不再提醒` 不等于删除；记录应仍可在单独清单或追溯入口找回。

### 12.6 防污染怎么检查
- 导入手稿提醒前后，页面 A 的金蝶提醒结果不应变化。
- 页面 B 改状态后，页面 A 的金蝶提醒结果不应变化。
- 页面 B 中 `不再提醒` 后，页面 A 的金蝶提醒结果不应变化。
- 页面 A 的下载 Excel / HTML 口径不应因为页面 B 手稿提醒导入而改变。
- 本阶段不验收金蝶提醒接入页面 B，不验收 `金蝶待更新` / `金蝶已同步`。
